# Versioning

- The specification uses **Semantic Versioning**: `MAJOR.MINOR.PATCH` with pre-release tags (`0.3.0-rc.1`). The current version is in [`CHANGELOG.md`](../CHANGELOG.md), the OpenAPI `info.version` fields and every schema's `$id` path (`/schemas/v0.3/`). From 0.3 on, the schemas of earlier minor releases stay unchanged in `schemas/v<major>.<minor>/` and on the website at their own `$id` paths. 0.1 and 0.2 were withdrawn with 0.3, before anyone used them (no consumers, no published integrations); their schemas are only in the git tags `v0.1.0` and `v0.2.0`.
- The **URL prefix** carries the major version: `/obx/v1`. Discovery advertises `obx_version` (`major.minor`) and `spec_version` (exact).
- **Minor** releases are additive: new optional fields, new endpoints, new capabilities, new enum values and vocabulary codes, new change types, new error and warning codes. Clients written for an older minor keep working because they MUST ignore what they do not know ([protocol.md §2](protocol.md#2-conventions)).
- **Major** releases may break conforming clients (removing or renaming fields, changing semantics). A node SHOULD serve the previous major (`/obx/v1` next to `/obx/v2`) for at least 12 months after a new major is released.
- **Patch** releases fix wording, examples and schemas that contradicted the prose; they never change behaviour on purpose.
- **Stability promise from 0.3.0.** 0.3.0 is the last release that changed existing shapes under `/obx/v1`. From 0.3.0 on, everything a consumer reads under `/obx/v1` and everything a brand's automation writes to `/obx/v1/ingest` changes **only by addition**, also before 1.0: no field, endpoint, enum value, vocabulary code, error code or query parameter is removed or renamed, no type changes, no optional request member becomes required, no default changes meaning. A change that cannot be made by addition waits for `/obx/v2`, which runs next to `/obx/v1` as described above. A node upgrade therefore never breaks a consumer written for 0.3 or later, and never expires cursors again for a change of shapes.
- **What "additive" may do**, and so what every client must be built for ([protocol.md §2](protocol.md#2-conventions) says how to treat each case): new optional members on any object, new values of any enumeration or vocabulary, new change types and webhook events, new capabilities, endpoints, query parameters, error codes and warning codes; a member that was always `null` getting values; wider limits. A new request member is always optional and its absence keeps the old behaviour.
- The exceptions are the ones a standard cannot avoid: a correction of a schema or example that contradicted the prose (patch), and a change needed to close a security hole, announced in the changelog under "Security". The import format (CSV/Excel) follows the same promise for files: a file that imports today imports the same way later; new columns and new accepted spellings may be added.
- 1.0 is the name for the moment the foundation takes this promise over; the goal is to freeze 1.0 after feedback from at least one external brand and one external consumer. Until 0.3.0, minor versions contained breaking changes (0.2 → 0.3); each is listed under "Breaking" in the changelog with a migration note.
- **Extensions** use `x-<vendor>-` field names and never collide with future standard fields. Popular extensions are candidates for standardisation in a minor release.
- The Node Admin + Portal API (`node-admin.yaml`) is versioned together with the reference nodes and the shared admin UI, not with the protocol; it may change in any minor release.
